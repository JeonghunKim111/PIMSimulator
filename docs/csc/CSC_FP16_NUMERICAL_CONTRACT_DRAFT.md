# CSC M7 FP16 numerical contract draft

## Target contract

The intended architectural path stores and operates on IEEE-754 binary16 from
matrix/x input through final y:

```text
matrix FP16 x x FP16
-> FP16-rounded product
-> FP16-rounded BGA ADD after every merge
-> FP16 partial transport
-> FP16-rounded GA ADD after every merge
-> FP16 final y
```

An FP64 SpMV is only an error oracle. It is not an architectural reference.
The bit-exact reference must consume exported FP16 matrix and x bits and replay
the actual descriptor, BGA, transport arbitration, and GA event order.

## Existing Samsung PIMSimulator semantics

| Property | Confirmed behavior and evidence |
|---|---|
| Type | `FP16.h` aliases `half_float::half`; implementation is `lib/half.h` version 2.1.0. |
| Bits | 1 sign, 5 exponent, 10 fraction bits; `fp16i` exposes the stored uint16 representation. |
| Default rounding | `HALF_ROUND_STYLE=std::round_to_nearest`; tie logic in `detail::rounded` selects an even LSB. |
| Conversion | `convertF2H(float)` invokes the half constructor; float/double conversion explicitly rounds to binary16. |
| Add | `half_float::operator+` returns a `half` and is documented/implemented as exact-to-rounding. |
| Multiply | `half_float::operator*` returns a `half` and is exact-to-rounding. |
| PIM ADD/MUL | `PIMBlock::add/mul` assigns the returned half to `BurstType::fp16Data_[lane]`; FP16 lane count is 16. |
| PIM MAC/MAD | Source expression is `half*half + half`; the multiplication operator returns a half before addition. Characterization proves this differs from `half_float::fma` for a selected input. |
| Subnormal | Library numeric limits report `denorm_present`; exact subnormal and underflow boundary tests pass. No flush-to-zero option is enabled. |
| Overflow | Round-to-nearest overflow produces signed infinity. |
| Inf/NaN | Infinity is preserved; NaN remains NaN and is quieted by conversion/operations. Payload preservation is not an architectural promise. |
| Signed zero | Conversion preserves sign; multiplication XORs signs; exact cancellation under nearest produces +0. |
| Build | C++17 `-O2`, no fast-math and no explicit F16C option in `Sconstruct`. |

`FP16SemanticsCharacterizationTest` validates all 65,536 stored bit patterns,
conversion midpoint behavior, min/max/subnormal/underflow/overflow, special
values, signed zero, ADD/MUL rounding, 16-lane PIM MUL, and separated MAC
rounding.

## Proposed CSC operations

The following is the M1 target, not yet implemented:

- Storage and serialization use the exact 16-bit representation.
- Source FP64/FP32 values convert exactly once through the canonical existing
  half constructor under round-to-nearest-even.
- `CSC FP16 MUL(a,b)` returns a stored half result before any later ADD.
- `CSC FP16 ADD(a,b)` returns a stored half result after every BGA or GA merge.
- Accumulators never retain a hidden FP32/FP64 intermediate.
- Partial transport carries FP16 bits without conversion.
- Final y exposes the exact FP16 bits generated by GA.
- Invalid lanes perform no arithmetic and generate no partial.

## Special-value policy

| Case | Draft policy |
|---|---|
| normal/tie | IEEE binary16 round-to-nearest-even |
| exact subnormal | preserve |
| inexact tiny value | round to subnormal or signed zero as binary16 requires |
| overflow | signed infinity under nearest |
| infinity | IEEE operation behavior |
| NaN | quiet NaN; compare by classification unless payload policy is later fixed |
| signed zero | preserve conversion/product sign; use existing half ADD cancellation behavior |

## Accumulation order

FP16 addition is not associative. A conventional CSC row loop is therefore
not a bit-exact oracle for M7. Required references are layered:

1. FP64 mathematical oracle for error reporting;
2. conventional sequential FP16 reference for algorithmic comparison;
3. event trace replay for architectural bit-exact validation.

The replay reference must use the same rounding primitive after every MUL and
every BGA/GA ADD and must follow eviction, drain, transport, and arbitration
order.

## Open decisions before M1 implementation

- [OPEN] Confirm that CSC uses separate rounded MUL and ADD even if a future
  implementation can invoke the existing PIM MAC instruction.
- [OPEN] Decide whether NaN payload/sign and signaling-to-quiet transformation
  are part of bit-exact output or only NaN classification.
- [OPEN] Decide whether compiler configurations enabling F16C are supported;
  if so, keep characterization in the release matrix.
- [OPEN] Define GA event order and capacity before its arithmetic reference can
  be finalized.

No CSC production type or arithmetic was changed during M0/M1-prep.
